# 05 — 证据方法与安全验证

[English](../05-methodology.md) · [项目首页](../../README.zh-CN.md)

## 证据等级

| 等级 | 含义 | 可支持的结论 |
| --- | --- | --- |
| A1 | 绑定产物/构建身份，按预声明判据直接观测 | 支持对该精确镜像和配置的主张 |
| A2 | 静态分析、交叉引用或间接运行时推理 | 支持设计与审查，不能单独证明运行时命题 |
| B | 未验证、有歧义或超出已采证范围 | 必须标为未知 |

静态反汇编能证明某指令读取 `task+0x898`，不能证明特定线程交错到达过它；实验室成功触发能证明该构建可达，不能证明所有同版本字符串内核均受影响。

## 判据先行流程

1. 写出要验证的不变量或分支。
2. 定义最小充分、不会修改权限的观测。
3. 记录精确源码与构建身份。
4. 每轮只改变一个独立变量。
5. 在隔离工程设备上重复运行。
6. 同时保留成功与失败结果。
7. 只把结论提升到证据实际支持的等级。

## 二进制分析纪律

- 用 ELF 符号/kallsyms 锚定函数入口，再解码精确镜像。
- 同时记录绝对地址和函数内相对偏移；公开日志避免实时绝对地址。
- 反编译只用于导航；常量、偏移、访问宽度、符号性和分支条件以机器指令为准。
- 关键字段尽量由独立生产者和消费者交叉确认。
- 仅在栈槽、调用约定和邻接数据均无歧义时，才用对象边界推断结构大小。
- 明确标注缺少 DWARF/BTF；不能把香草内核布局静默套入厂商镜像。

## 补丁审查纪律

把修复看成一次不变量转换：

| 修复前 | 修复后 |
| --- | --- |
| 由执行上下文选择清理任务 | 由 waiter 所有权选择清理任务 |
| 可能持有错误任务的 `pi_lock` | 持有真实 waiter 任务的 `pi_lock` |
| 真实任务可残留 `pi_blocked_on` | waiter 生命周期结束前清空真实任务 |
| 链调整收到 `current` | 链调整收到 `waiter_task` |
| 部分初始化缺少独立保护 | 检查自死锁/早期错误前置条件 |

补丁能够干净应用并不等于正确。Android 厂商树常修改 rtmutex 类型、函数签名、trace hook 与锁包装器。

## 回归覆盖

最小矩阵包括：

- 普通 PI 锁获得与释放；
- 代理 requeue 成功与回滚；
- 超时与信号中断；
- owner 退出/恢复路径；
- top 与 non-top waiter；
- 嵌套优先级捐赠链；
- waiter 初始化前后的自死锁；
- PI 状态活动时改变调度策略/优先级；
- 平台支持时的 CPU 迁移与取消压力。

每一项都验证返回语义、无陈旧 `pi_blocked_on`、任务锁身份正确、cached RB 根/leftmost 一致、引用平衡，并确认 lockdep/KASAN/KCSAN 无报告。

## 公开纪律

安全文档应让修复可复核，而不是让提权可即插即用。可包含根因、不变量、源码级修复、受影响代码识别与安全回归测试；应排除可操作内存回收时序、伪造内核对象、实时目标、权限修改和预编译载荷。

## 如何表达不确定性

“未能确证”本身是有用结论。常见原因有厂商源码缺失、无 DWARF/BTF、helper 被内联而无稳定符号边界、运行时仪器不足。应写明闭环还缺哪类证据，不能用上游假设填空。
